# E09. Совпадение имени локальной и доменной учётных записей

**Дата:** 9 октября 2026 года. **Статус:** выполнено на pc2; обнаруженное расхождение аутентификации и идентичности сеанса устранено в проверенных условиях.

## Вопрос и ожидаемый результат

Как ALT Workstation различает локального и доменного пользователя с одинаковым коротким именем? Достаточно ли ввода `e09same@lab.test`, чтобы графический сеанс получил доменный UID, домашний каталог и группы?

Ожидается, что локальный `e09same` и доменный `e09same@lab.test` остаются разными учётными записями. После нового входа UID, группы, домашний каталог и билет должны соответствовать выбранному источнику. Успешная проверка пароля сама по себе не подтверждает идентичность созданного сеанса.

## Ход опыта

### 1. Доменная запись и контрольный вход

На dc1 под root выполнено:

```bash
samba-tool user add e09same --userou='OU=Lab'
samba-tool user show e09same --attributes=distinguishedName,sAMAccountName,userPrincipalName,objectSid,userAccountControl
```

Получены `CN=e09same,OU=Lab,DC=lab,DC=test`, UPN `e09same@lab.test` и `userAccountControl: 512`. На pc2 локальной записи ещё нет; запросы через SSSD и общий NSS возвращают доменного пользователя с UID `1164001108`, GID `1164000513` и `/home/LAB.TEST/e09same`.

Первый графический вход доменного пользователя успешен: UID `1164001108`, доменный домашний каталог и TGT для `e09same@LAB.TEST`, выданный в 19:29:40. Подтверждения: [создание](../evidence/09-10-2026/11-dc1-e09same-created.png), [исходный доменный сеанс](../evidence/09-10-2026/12-pc2-e09same-domain-baseline.png).

### 2. Создание локального пользователя с тем же именем

При работающем SSSD команда под root на pc2:

```bash
useradd -m -d /home/e09same -s /bin/bash -c "E09 local account" e09same
```

завершилась с сообщением «пользователь „e09same“ уже существует» и кодом `9`, хотя запрос `getent -s files passwd e09same` не вывел локальной записи. Доменный тёзка был доступен через SSSD. [Кадр отказа](../evidence/09-10-2026/13-pc2-e09same-useradd-refused.png).

Для подготовки именно этого опыта из локального административного сеанса выполнено:

```bash
systemctl stop sssd
SSS_NSS_USE_MEMCACHE=NO useradd -m -d /home/e09same -s /bin/bash -c "E09 local account" e09same
echo "useradd exit code: $?"
systemctl start sssd
systemctl is-active sssd
```

Получены код `0` и SSSD `active`. Переменная задавалась только для одного запуска команды. После этого локальный пользователь имеет UID/GID `1001:1001`, а доменная запись сохраняет `1164001108:1164000513`. Общий запрос короткого имени выбирает локальную запись; полное имя возвращает доменную, но её поле имени до исправления всё ещё равно `e09same`. [Два источника](../evidence/09-10-2026/14-pc2-e09same-two-account-sources.png).

Локальный пароль установлен через `passwd e09same`; команда сообщила об успешном обновлении после предупреждения о слабом пароле. Пароли в материалы проекта не включаются. Проверка доменной парольной политики E03 этим действием не выполнена.

### 3. Предварительные наблюдения интерфейса и групп

После выхода список GDM показал `E09 local account`, а доменная карточка перестала отображаться. Первое открывшееся окно терминала ещё содержало доменный UID и прежний TGT 19:29:40. Пользователь предположил сохранение старого сеанса; этот эпизод не используется как доказательство приёма локального пароля доменной записью.

При явном выборе `E09 local account` подтверждены UID `1001`, `/home/e09same` и отсутствие Kerberos-кеша этого UID. Однако процесс получил дополнительную доменную группу `1164000513` и локальные группы ролей. `loginctl` тогда показывал только сеансы UID `1001`; `getent initgroups` для короткого и полного имени выдавал одинаковый набор доменных и локальных дополнительных групп.

Таким образом, до исправления смешивались и результаты получения групп. Подпись карточки сама по себе не определяет UID процесса. [Список входа до исправления](../evidence/09-10-2026/15-pc2-e09same-login-list-before-fix.png).

### 4. Контрольная проверка после перезагрузки: сбой

После перезагрузки pc2 введены полное имя `e09same@lab.test` и, по сообщению пользователя, доменный пароль. Новый графический сеанс получил:

Проверка                    | Фактический результат
----------------------------|---------------------------------------------------------------
UID / основной GID          | `1001:1001` — локальная запись
Домашний каталог и владелец | `/home/e09same`, `1001:1001`
Дополнительные группы       | Включают доменную `1164000513`
`KRB5CCNAME`                | `KEYRING:persistent:1164001108` — доменный UID
`klist`                     | `Invalid UID in persistent keyring name while resolving ccache`
`loginctl`                  | Новый пользовательский сеанс 3 и manager-сеанс 4, оба UID `1001`

Журнал того же запуска в 19:58:18 фиксирует `pam_sss(gdm-password:auth): authentication success` для `user=e09same@lab.test`, затем `pam_tcb(gdm-password:session): Session opened for e09same`. Позднее строка D-Bus содержит `session uid=1001`.

**Подтверждённый сбой:** доменная аутентификация через SSSD завершилась успешно, но созданный сеанс использовал локальную числовую идентичность. `uid=0` в строке PAM относится к привилегированному процессу проверки и не означает вход пользователя как root. [Команды и журнал](../evidence/09-10-2026/16-pc2-e09same-auth-session-collision.txt).

### 5. Анализ NSS/PAM и рабочая гипотеза

В подключаемом стеке PAM сначала проверяется наличие пользователя в локальной базе; для отсутствующего локально пользователя с UID не менее `65536` выбирается SSSD-путь. В общем auth-стеке включён `pam_canonicalize_user.so`. Передача полного имени в NSS до изменения возвращала запись с коротким полем имени, которое совпадало с локальным логином.

Рабочая гипотеза: при обработке имени в цепочке GDM/PAM/NSS доменное имя сводилось к короткому, после чего дальнейший выбор учётной записи попадал в `files`. Документация ALT описывает канонизацию имени через базу пользователей [2]. Точный компонент и момент изменения `PAM_USER` в этом опыте трассировкой не установлены; дефект конкретного модуля не объявляется доказанным.

### 6. Полные доменные имена в SSSD

На pc2 сохранена резервная копия и изменён раздел домена:

```bash
cp -a /etc/sssd/sssd.conf /root/sssd.conf.e09-before-fq-2026-10-09
sed -i '/^\[domain\/LAB\.TEST\]$/a use_fully_qualified_names = true' /etc/sssd/sssd.conf
systemctl restart sssd
systemctl is-active sssd
```

Это запись уже выполненных действий; повторять вставку строки в текущей конфигурации не требуется. Параметр полных имён описан в документации SSSD [1].

После изменения короткое имя возвращает локальную запись, а полное — `e09same@LAB.TEST` с доменным UID. `getent -s sss passwd e09same` ничего не выводит. Новые графические входы разделены правильно: доменный UID `1164001108` с его домашним каталогом и TGT; локальный UID `1001` с локальным каталогом и без доменного Kerberos-кеша. Написание суффикса `LAB.TEST` в результате SSSD отличается регистром от введённого `lab.test`; в выполненном входе оба относятся к этому домену.

Возник побочный эффект: доменные пользователи перестали получать прежние локальные группы ролей. У e09same осталась только `domain users@LAB.TEST`; у student2 сохранились две доменные группы, включая `lab-students@LAB.TEST`. [Доменный сеанс](../evidence/09-10-2026/17-pc2-e09same-domain-login-fq.png), [локальный сеанс](../evidence/09-10-2026/18-pc2-e09same-local-login-fq.png).

### 7. Дополнение ролей и итоговые входы

Сначала получены `rolelst` и `rolelst -V`. Вывод до изменения не содержит отдельной связи доменной группы с ролью `users`. Сохранены настройки ролей и добавлена явная связь с полным именем группы:

```bash
tar -czf /root/roles-e09-before-update-2026-10-09.tar.gz -C /etc role role.d
echo "backup exit code: $?"
roleadd 'domain users@LAB.TEST' users
rolelst
id e09same@lab.test
id student2@lab.test
id e09same
```

Код резервного копирования — `0`; в `rolelst` появилась строка `domain users@LAB.TEST:users`. У доменных e09same и student2 снова получены локальные группы роли users и её вложенных ролей; у локального e09same доменные группы отсутствуют. Механизм ролей описан в документации ALT [3]. Добавление `localadmins` или `wheel` этим действием не выполнялось.

После повторного запуска и новых графических входов итог подтверждён отдельно для двух пользователей:

Признак         | Доменный вход `e09same@lab.test`       | Локальный вход `e09same`
----------------|----------------------------------------|-------------------------
Имя в `id`      | `e09same@LAB.TEST`                     | `e09same`
UID             | `1164001108`                           | `1001`
Основной GID    | `1164000513`                           | `1001`
Группы процесса | Доменная группа и группы роли users    | Только локальная `1001`
`$HOME`         | `/home/LAB.TEST/e09same`               | `/home/e09same`
Kerberos        | TGT `e09same@LAB.TEST`, выдан 20:41:21 | Кеш UID `1001` не найден

Подтверждения: [итоговый доменный сеанс](../evidence/09-10-2026/19-pc2-e09same-domain-login-with-roles.png), [итоговый локальный сеанс](../evidence/09-10-2026/20-pc2-e09same-local-login-final.png), [список GDM](../evidence/09-10-2026/21-pc2-e09same-login-list-after-fix.png). Видимая подпись доменной карточки GDM остаётся `e09same`; различение подтверждается результатами сеансов.

## Вывод, ограничения и сохранённое состояние

E09 является завершённым экспериментом на pc2: до появления локального тёзки доменный вход работал, после его создания обнаружена коллизия, сбой подтверждён новым входом после перезагрузки, затем проверены разделение имён и восстановление обычных ролей. Учётные записи различаются прежде всего UID/GID и источником, а строка имени в интерфейсе и успешная аутентификация дают только часть картины.

Проверена последовательность изменений `use_fully_qualified_names = true` и добавления доменной группы в роль users. Отдельный обратный опыт с возвратом коротких имён не выполнялся; точная причина внутри цепочки PAM/NSS остаётся гипотезой. На pc1 опыт не повторён. Доступ к устройствам, работе офлайн, политике паролей и конкретным GPO эти проверки не посвящались. Запрос `id student2@lab.test` подтверждает сохранение членства E02 на pc2, но новый графический вход student2 после исправления не повторялся.

Доменный пользователь E09 создан через `samba-tool`; опыт не устанавливает дефект ADMC и не заменяет E06/E07. Сообщение об отказе исполнения `su` из тестовой учётной записи зафиксировано как отдельное ограничение; административные действия выполнены из `gudzichek-pc2`.

В `/root` на pc2 сохранены копия SSSD и архив ролей; их восстановление не проверялось. Сообщено о финальных снимках `after-e09-2026-10-09` dc1, pc1 и pc2. На dc1 сохранён новый доменный объект, на pc2 — локальный тёзка, настройка полных имён и роль; на pc1 изменение SSSD в E09 не выполнялось. Следующий этап — E05 по [плану исследования](../docs/research.md#14-статус-проверок-и-следующий-этап).
