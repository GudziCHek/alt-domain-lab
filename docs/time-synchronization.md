# Синхронизация времени: диагностика и исправление 10 октября

## Проблема

Во время E05 часы pc2 заметно отставали: на кадре рабочего стола показано 10:33, при времени хоста около 10:52. Проверка date подтвердила отставание системных часов; часовой пояс Europe/Moscow был правильным. На pc1 время выглядело близким к реальному, но Chrony также не был синхронизирован.

Это наблюдение и исправление настройки стенда, а не новый эксперимент с отдельным номером. Получение общей настройки фона и успешный вход не заменяют проверку времени.

## Диагностика

Узел | Состояние до исправления                                 | Основание
-----|----------------------------------------------------------|----------------------------------------------------------------
dc1  | Синхронизирован с внешним NTP, но не обслуживает pc1/pc2 | Leap status=Normal; оба accheck: 209 Access denied; ss не показывает UDP 123
pc1  | Chrony active, синхронизации с dc1 нет                   | Reference ID=00000000; Stratum=0; Leap status=Not synchronised; ^? 10.77.0.10, Reach=0
pc2  | Такое же состояние, заметное отставание часов            | Те же признаки Chrony; timedatectl synchronized=no; date около 10:42 при реальном времени около 11:00

На обоих клиентах единственным показанным NTP-источником был 10.77.0.10. На dc1 в конфигурации действовала pool pool.ntp.org iburst; разрешение allow было только закомментированным примером. Chrony по умолчанию не обслуживает клиентов без разрешения доступа [1].

**Установленная ошибка настройки:** клиентам запрещено использовать dc1 как NTP-сервер. Отсутствие ответов и успешная синхронизация после разрешения доступа подтверждают этот разбор. Причина накопления именно такого отставания виртуальных часов отдельно не установлена.

Проверки выполнялись командами hostname, date, timedatectl, chronyc tracking, chronyc -n sources -v, chronyc accheck и ss -lunp 'sport = :123'. Активная служба показывает запуск процесса; выбранный источник и Leap status показывают состояние Chrony. Значение System time около нуля при Reference ID=00000000 не является доказательством точных часов.

Подтверждения: [dc1 до исправления](../evidence/10-10-2026/15-dc1-ntp-client-access-denied.png), [конфигурация](../evidence/10-10-2026/16-dc1-chrony-config-before-fix.png), [текст клиентов до исправления](../evidence/10-10-2026/ntp-clients-before.txt).

## Исправление на dc1

Перед правкой в инструкции предусмотрена копия /root/chrony.conf.before-ntp-fix-2026-10-10. Отдельный вывод создания копии не передан; она не включена в репозиторий.

В /etc/chrony.conf добавлено разрешение сети стенда:

```text
allow 10.77.0.0/24
```

После перезапуска chronyd подтверждены active, два ответа 208 Access allowed, сокет 0.0.0.0:123 процесса chronyd и Leap status=Normal. В последнем кадре контроллер выбрал внешний источник time.cloudflare.com из своего набора; ранее выбранный IP был другим. Ручная замена pool на Cloudflare этим кадром не подтверждается.

Выполненные команды проверки:

```bash
systemctl restart chronyd
systemctl is-active chronyd
chronyc accheck 10.77.0.21
chronyc accheck 10.77.0.22
ss -lunp 'sport = :123'
chronyc tracking
```

[Скриншот результата dc1](../evidence/10-10-2026/19-dc1-ntp-client-access-allowed.png), [его расшифровка](../evidence/10-10-2026/dc1-ntp-fix.txt).

## Исправление на клиентах

На pc1 и pc2 из локальной административной учётки под root выполнены:

```bash
systemctl restart chronyd
chronyc burst 4/4
chronyc -n sources -v
chronyc tracking
```

После ожидания оба клиента выбрали dc1 (^*). Только после получения пригодных измерений выполнена chronyc makestep, чтобы убрать остаточное смещение системных часов. Затем повторены date, timedatectl и tracking. Действия относятся к уже выполненному исправлению; повторять makestep при исправном времени не требуется.

Проверка после исправления                  | pc1                              | pc2
--------------------------------------------|----------------------------------|---------------------------------
Reference ID                                | 0A4D000A (10.77.0.10)            | 0A4D000A (10.77.0.10)
Выбранный источник                          | ^* 10.77.0.10                    | ^* 10.77.0.10
Leap status                                 | Normal                           | Normal
System clock synchronized                   | yes в повторном запросе 11:14:42 | yes в повторном запросе 11:19:50
Новая выдача TGT student2 после исправления | 11:23:24                         | 11:24:56

У pc1 сначала был stratum 5, у pc2 позднее — 4: уровень выбранного источника dc1 между измерениями изменился. Сами по себе разные stratum не показывают рассинхронизацию клиентов. Точные значения и время измерений сохранены в текстах; System time оценивается вместе с состоянием источника.

Сразу после makestep timedatectl на обоих клиентах ещё показывала no, затем стала yes. Зафиксирован переход состояния, точная внутренняя задержка обновления флага не исследована. Дополнительная правка конфигурации для этого перехода не выполнялась.

Подтверждения: [pc1 после исправления](../evidence/10-10-2026/pc1-ntp-after.txt), [pc2 после исправления и поздняя проверка yes](../evidence/10-10-2026/pc2-ntp-after.txt), [сеанс pc1 с новым TGT](../evidence/10-10-2026/21-pc1-e05-wallpaper-unlocked-session.png), [сеанс pc2 с новым TGT](../evidence/10-10-2026/22-pc2-e05-wallpaper-unlocked-session.png).

## Текущее состояние и дальнейший контроль

Рабочая схема: внешний NTP-пул → dc1 → pc1/pc2. Контроллеру разрешено обслуживать сеть 10.77.0.0/24; выбранный источник клиентов подтверждён напрямую. Новые доменные сеансы после исправления получают TGT с согласованным текущим временем.

После запуска или восстановления ВМ достаточно сначала проверить:

```bash
date '+%F %T %Z %z'
timedatectl status
chronyc tracking
chronyc -n sources -v
```

Синхронизация зависит от доступности dc1, а внешняя точность — от его источников. Работа без внешней сети и восстановление снимков отдельно не проверены. Kerberos требует согласованных часов; стандартный clockskew MIT Kerberos составляет 300 секунд [3]. Допуск в этом стенде не увеличивался.
